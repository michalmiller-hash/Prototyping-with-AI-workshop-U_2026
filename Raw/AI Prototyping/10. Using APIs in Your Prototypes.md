# 



APIs unlock enormous potential for your prototypes by connecting them to external services and data sources. In this lesson, you'll learn how to integrate third-party APIs into your prototypes—from simple REST API calls to working with large language models (LLMs). We'll walk through practical examples of adding AI capabilities, pulling in external data, and connecting to services your users already rely on, transforming your prototypes from standalone demos into tools that integrate with the real world.

APIs let your prototypes connect to the outside world—live weather data, real photos, AI that actually thinks. Instead of faking complex features, you can plug into the same services that power production products: Stripe for payments, Google Maps for location data, OpenAI for text generation. The result is a prototype that feels more authentic—because it is.

By the end of this lesson, you'll have made your first API call, chained multiple APIs together, and built an LLM-powered feature in Lovable without writing a single line of backend code. Let's get into it.

## 

## What is an API?

In [Software Architecture for Non-Technical Builders(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14115:6755/prototyping-fundamentals), we introduced APIs as one of the four key elements of modern software architecture. Now let's go deeper into how they work and how to use them in your prototypes.

An **API** (Application Programming Interface) is a structured way for one piece of software to request something from another—defining what you can ask for, how to ask for it, and what you'll get back.

Think of it like a restaurant. You're the customer. The API is the menu. When you are ready to order something, you "call" the waiter (just as you "call" an API). You place your order, and your food arrives—you don't need to see inside the kitchen or know how the food is prepared. You just need to know what's on the menu and how to order.

APIs work the same way. When your prototype needs to generate text via an LLM, process a payment, or look up a location, it calls an API—sending a request to someone else's server and getting a result back. You don't need to understand the complicated machinery behind the scenes. You just need to know the interface: how to send a request in a format the service understands.

### 

## Why APIs matter for prototyping

APIs let your prototype tap into real capabilities without building them yourself:

- Want AI-powered features? Call the OpenAI or Anthropic API.
    
- Need maps? Google Maps API.
    
- Email notifications? SendGrid API.
    
- Analytics tracking? Amplitude, Mixpanel, or PostHog API.
    
- Need product functionality? Use internal APIs.
    

This is a fundamental shift from the clickable prototypes of the past, where complex features had to be faked. With APIs, your prototype can actually _do things_—making it far more useful for testing with real users.

### 

## When to use APIs

Just because you _can_ call an API doesn't mean you _should_. APIs add complexity, and that complexity should be justified by the decision you're trying to make. As we discussed in [The New Product Development Lifecycle(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14114:6754/introduction-to-prototyping), prototypes are decision-making tools—scope them accordingly. 

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/prototype-api-strategy.svg)

### Start with mocked data

In many cases, you can mock an API's response with hard-coded data. This is often perfectly fine for concept prototypes used for brainstorming or design prototypes used to define interactions. You may even get away with it for research prototypes, depending on what supports your participants' **suspension of disbelief**.

For example, imagine you're prototyping a trip itinerary feature. In production, the feature might call an attractions API to return a dynamic list of recommended places. But for a prototype, you could hard-code 20–30 attractions and focus on the UX of creating and managing an itinerary. That makes sense if you're testing the experience. However, if you want to test the quality of recommendations for different kinds of travelers, your prototype may need to connect to a live API with real data.

### Client-side API calls

Recall from [Software Architecture for Non-Technical Builders(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14115:6755/prototyping-fundamentals) that web products have a client-side frontend (the browser) and often a server-side backend. In production, the frontend typically talks to your own backend rather than calling third-party APIs directly—the backend protects secrets, enforces permissions, and coordinates multiple systems.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/software-architecture.svg)

That said, some services are designed to be called directly from the browser. Analytics tools like Amplitude need to fire from the browser to capture user behavior accurately. Stripe.js collects payment info directly in the browser for security reasons. These are legitimate client-side API calls even in production.

For prototyping, the rules are more relaxed. You may choose to call an API directly from the frontend—even one that would normally go through a backend—for simplicity and speed. This is perfectly fine in a controlled environment where security and scalability tradeoffs are acceptable.

### Server-side API calls

So when _would_ you use a backend for API calls? It depends on your tool. Many prototypes are frontend-only—especially those built with dedicated AI prototyping tools like Reforge Build, Magic Patterns, and Alloy, which focus primarily on frontend experiences. But AI app builders like Lovable, Bolt, and Replit—along with AI development tools like Claude Code and Cursor—support both frontend and backend functionality, and will often route API calls through the server automatically.

We'll see this trade-off in practice. We'll start by building a couple of prototypes that are frontend only. Later in this lesson, we'll rebuild one of our prototypes in Lovable, and we'll use Lovable Cloud to add LLM-powered features that require server-side integration.

Your prototyping tool will often make these architectural decisions for you—you don't need to specify whether something runs on the frontend or backend. But knowing the distinction helps when debugging. If an API call fails, understanding whether it's running in the browser or on the server points you toward the fix much faster.

### 

## API keys

When you use someone else's API, they give you an **API key**: a unique code that identifies your application. Think of it as a password that lets you log in to the API. The key lets the provider track your usage, enforce rate limits, and charge you for what you use.

Like passwords, API keys should be kept secret. In production code, API keys are managed very carefully. They aren't put in frontend code (where anyone can inspect them in the browser), and they aren't committed directly to your codebase. Instead, they are stored in environment variables—configuration values kept securely outside your code. Your backend reads the key from the environment variable when it needs to call the API, so the key never reaches the browser.

Every app builder (such as Lovable, Bolt, and v0) and every development tool (such as Cursor and Claude Code) supports environment variables for securely storing API keys. Prototyping tools like Reforge Build and Alloy don't support them, since they are designed to generate prototypes for validation rather than production applications that call external APIs.

### 

## REST APIs and endpoints

In [Software Architecture for Non-Technical Builders(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14115:6755/prototyping-fundamentals), we introduced REST APIs—the most common convention for how APIs are structured. A quick refresher: REST APIs combine an HTTP method (GET, POST, PUT, DELETE) with an **endpoint** (a URL) to define exactly what you're asking for:

- GET /api/trips — Retrieve all trips
    
- POST /api/trips — Create a new trip
    
- GET /api/trips/123 — Retrieve trip 123
    
- PUT /api/trips/123 — Update that trip
    
- DELETE /api/trips/123 — Remove that trip
    

What matters most for prototyping is that every API publishes **documentation** describing its available endpoints—what you can request, what parameters are required, and what the response looks like. The docs are your reference when integrating an API, and sharing the documentation URL with your AI tool will significantly improve the results.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/apis-request-response.svg)

For example, Spotify's "Get Artist's Albums" endpoint is documented here: [https://developer.spotify.com/documentation/web-api/reference/get-an-artists-albums(opens in a new tab)](https://developer.spotify.com/documentation/web-api/reference/get-an-artists-albums).

From that page, you can quickly pull the key details you'd give an AI tool:

- **HTTP method + endpoint:** GET /artists/{id}/albums
    
- **Required path parameter:** id (Spotify ID of the artist, e.g. 0TnOYISbd1XYRBk9myaseg)
    
- **Common query parameters:** include_groups (filter to album, single, appears_on, compilation), market (country code), limit, offset
    
- **What comes back:** a paginated list of simplified album objects (including fields like name, release_date, images, and links like external_urls.spotify)
    

This is a pattern you'll use throughout this lesson: find the API docs, identify the key details, and share them with your AI tool.

## Fetching live data from Open-Meteo

Open-Meteo is a free, open-source weather API that requires no API key and works perfectly from the browser. It's our ideal starting point.

Go to [open-meteo.com(opens in a new tab)](http://open-meteo.com/) to learn more about the API. Let’s look at what a GET request looks like for that API:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/qyu12v/Screenshot%202026-03-09%20.png)

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/api-url-anatomy.svg)

Let's break that down:

- [https://api.open-meteo.com/v1/forecast(opens in a new tab)](https://api.open-meteo.com/v1/forecast) — This specifies where to go for the service.
    
    - GET (not shown) - this specifies the HTTP method that we discussed above. APIs default to GET if another method is not specified.
        
    - [api.open-meteo.com(opens in a new tab)](http://api.open-meteo.com/) - This is the domain of where the service is available. API services are available at URLs just like websites.
        
    - /v1 - specifies to use the first version of the API. APIs often have versions so that if something changes it doesn't break existing apps that are using the API. The app can upgrade the version of the API they're using when they are ready and the service continues to provide that previous version until it is sunset.
        
    - /forecast - This is the specific route that we want. Routes are used to provide different tasks or operations.
        
- ?latitude=37.7749&longitude=-122.4194&current=temperature_2m,weathercode - Everything after the question mark are the **query parameters**. The parameters tell the API exactly what you're looking for, and each parameter is separated by a &.
    
    - latitude and longitude — coordinates for San Francisco
        
    - current=temperature_2m,weathercode — we want current temperature (in meters above ground, which is just standard surface temperature) and a numeric weather code that represents conditions like "clear sky," "rain," or "snow"
        

Now let's update the weather card to use live data. Give Reforge Build this prompt:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/0CQ05m/Screenshot%202026-03-09%20.png)

In this prompt, we’ve both specified which API we want to use and pointed the prototyping tool towards the documentation for that API. Although we could have asked the tool to add live weather without being specific about the API, we’d be leaving a critical choice to the AI which could introduce challenges as we iterate.

Run the prototype and your weather card now shows real, live data. The temperature and condition update automatically based on what Open-Meteo returns. Refresh the page and you'll see the data is fresh each time. We can also select from different cities to confirm that our data is no longer hard-coded.

### Under the hood

If you peek at the code Reforge Build generated, you'll see something like this at the core of the component:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/Screenshot%202026-03-09%20.jpg)

A few things worth noticing:

- **The URL is the REST API call we discussed above.** You can see the same endpoint ([api.open-meteo.com/v1/forecast(opens in a new tab)](http://api.open-meteo.com/v1/forecast)) and the same query parameters (latitude, longitude, current) that we broke down earlier. The difference is that the values are now dynamic—${[city.lat(opens in a new tab)](http://city.lat/)} and ${city.lon} plug in the coordinates of whichever city the user selected, so a single line of code can fetch weather for any location.
    
- **fetch sends the request and parses the response.** fetch is JavaScript's built-in way of making an API call. It sends a GET request to the URL, waits for the response, and .json() parses the result into a JavaScript object. This is the same mechanism behind every API call in every web app—your AI tool just wrote it for you.
    
- **The API response is just structured data.** The call returns a JSON object with fields like data.current.temperature_2m and data.current.weather_code. The code picks out exactly the fields it needs and ignores everything else. This is how every API integration works—you get back more data than you need and extract the pieces that matter.
    
- **Raw data gets transformed into something useful.** The API returns a numeric weather code (e.g., 0 for clear, 61 for rain), not a human-readable label. The generated code includes a weatherCodeToStatus function that maps those codes to labels like "Clear" or "Rain," which then drive both the text display and which weather icon to show. This kind of data transformation—turning raw API output into something your UI can use—is a common pattern you'll see in every API integration.

## Building with multiple APIs

You've already chained two APIs together in the weather card—the Geocoding API to convert a city name into coordinates, then the Forecast API to fetch the weather. Now let's take it further and build something more interesting.

The idea: a geography trivia game that doesn't just reveal the right answer, it shows you the _current weather_ and a _relevant photo from_ that location.

### 

## Combining APIs: Geography Trivia + Weather

The Open Trivia DB is a free, community-contributed trivia API that requires no key and works from the browser. It returns questions filterable by category, difficulty, and type. Category 22 is Geography—exactly what we want.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/__-ohR/Screenshot%202026-03-09%20.png)

Let's break that down:

- https://opentdb.com/api.php — This specifies where to go for the service.
    
    - GET (not shown) — the default HTTP method, just like before.
        
    - opentdb.com — the domain for the Open Trivia Database service.
        
    - /api.php — the route that handles trivia question requests.
        
- ?amount=1&category=22&type=multiple — the **query parameters**, each separated by &.
    
    - amount=1 — we want one question per request
        
    - category=22 — category 22 is Geography (Open Trivia DB assigns a number to each topic)
        
    - type=multiple — we want multiple-choice questions (four options) rather than true/false
        

A typical response looks like this:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/_S1yNS/Screenshot%202026-03-09%20.jpg)

Note that the answers come back separately—the correct answer and the wrong answers are in different fields. You'll want to mention this in your prompt so the AI combines and shuffles them before displaying.

### 

### Building the prototype

Here's the full flow of the "Where in the World?" prototype:

1. Fetch a geography question from Open Trivia DB
    
2. Display question with shuffled multiple-choice answers
    
3. User selects an answer
    
4. Reveal: show whether they were right
    
5. Extract the location from the correct answer
    
6. Geocode that location → get coordinates
    
7. Fetch current weather for those coordinates
    
8. Display: answer card + "Right now in [city]: [temp] and [condition]"
    

This is where a well-structured prompt makes a big difference. Rather than asking for each piece separately, describe the complete flow upfront so Reforge Build can wire the APIs together correctly:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/QqLO9C/Screenshot%202026-03-09%20.png)

Your prototype will look something like this:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/image%20%289%29.png)

The key lesson here isn't the generated code—it's the pattern. Each API in the chain transforms data into something the next API can use. The Open Trivia API gives you a location name as text. Open-Meteo’s Geocoding API turns that text into coordinates. Open-Meteo’s Forecast API turns those coordinates into current temperature and conditions. At each step, the data is reshaped into the right format for the next call.

This composition—wiring APIs together so the output of one feeds the input of the next—is an important skill of working with APIs. Once you see it, you'll apply it everywhere and your prototypes will be better as a result.

## Working with API keys: Unsplash

So far, every API we've used has been completely free and keyless. That's by design—it removes all friction from your first explorations. But most of the powerful APIs you'll want in your prototypes require a key, so let's demystify that.

### Getting an Unsplash key

Unsplash is a photo platform with a developer API that lets you search for high-quality photos by keyword. It's one of the friendliest APIs to get started with—the signup is instant and there's no approval process.

Here's the full setup:

1. Go to [unsplash.com/developers(opens in a new tab)](https://unsplash.com/developers)
    
2. Create a free account or log in
    
3. Click "New Application"
    
4. Accept the API guidelines (worth reading—they require photo attribution)
    
5. Your Access Key appears immediately on the next screen
    

Total time: about three minutes. No credit card, no review process, no waiting.

### Under the hood: how API keys are passed

If you look at the generated code, you'll notice the Unsplash key is passed differently than the Open-Meteo parameters:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/6yIyls/Screenshot%202026-03-09%20.png)

The key is sent in a **header**—metadata that travels alongside the request—rather than in the URL itself. Many APIs use headers for authentication because it keeps keys out of server logs and browser history. You don't need to remember this detail; just include the API's authentication instructions in your prompt and the AI tool will handle the rest.

### The security reminder

For this prototype, the Unsplash key lives in frontend code—visible to anyone who opens browser developer tools. That's an acceptable tradeoff for a prototype because:

- Unsplash demo keys are read-only (they can search photos, not delete them)
    
- The rate limit is low (50 requests per hour), so misuse has a natural ceiling
    
- This is a prototype, not a production app
    

But get into the habit of recognizing this as a temporary shortcut. In the next section, you'll see how Lovable handles API keys properly—storing them securely on the server so they never reach the browser.

## Using APIs from the backend

Everything we've built so far has run in the browser—including those API keys. As your needs grow, you'll want backend support: infrastructure that handles databases, authentication, and business logic securely on the server rather than in the browser.

Each prototyping tool takes a different approach to the backend. Some focus entirely on frontend prototyping. Others provide backend support through Supabase, a “backend as a service” platform that makes it easy to add server-side capabilities. A few tools, like Lovable, have built their own backend platforms.

[**Lovable Cloud**(opens in a new tab)](http://lovable.dev/cloud) is Lovable's built-in backend, and the feature most relevant here is its support for **secure server-side connections** to external services. Lovable Cloud runs your API calls on the server, so API keys and sensitive data never reach the browser. This is how you'd safely connect to payment providers, email services, or any API where exposing the key in frontend code would be a risk.

Lovable takes this a step further with **Lovable AI**, which lets you add LLM-powered features—like content summarization, image generation, or document Q&A—directly through a prompt. You don't need to manage API keys or configure OpenAI or Gemini yourself; Lovable handles the connection and bills usage through your account. If you want your prototype to use AI, this is the fastest way to get there.

In this section, we’ll rebuild our trivia app as a full-stack app in Lovable that securely calls the Unsplash API and uses an LLM to generate text.

## The API ecosystem: your building blocks

In a few minutes, we built a full-stack app with integrations to four different services (Open-Meteo for weather, Open Trivia for trivia questions, Unsplash for photos, and OpenAI for text generation).

That's the magic of APIs. They offer you building blocks that you can snap together to get powerful capabilities very quickly. Let's take a quick look at the different types of APIs available to you.

## Internal APIs

Some of the most valuable APIs for prototyping aren't public—they're internal. Most companies have internal APIs—endpoints that access proprietary data, trigger workflows, or pull from internal systems. Product catalogs, customer records, transaction history, recommendation engines, pricing logic, inventory—these are all commonly available through internal endpoints. Connecting your prototype to real company data makes it far more realistic than anything you could build with public data alone, and it's often the fastest path to a high-fidelity experience.

Internal APIs typically require company credentials or OAuth tokens—your engineering team can set you up. And unlike public APIs, they may not have polished documentation, so it's helpful to provide your AI tool with as much context as possible—sample responses, field names, authentication details. You may also need to debug API requests and responses to get the output you want. With the material we've covered in this lesson, you'll be able to do exactly that.

## Common external APIs every builder should know

Here's your reference map for the building blocks most product teams reach for:

We've just built a couple of very capable prototypes, but there is one essential thing that is missing: data that persists.

Right now, if a user finishes a round of the trivia game, closes the tab, and comes back tomorrow—everything is gone. Their score, their history, which questions they've already seen. None of it survives a page refresh. That's fine for a one-session prototype in a research study. But it limits what you can learn from users who return.
