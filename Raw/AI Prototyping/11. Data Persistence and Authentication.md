# 


Most prototypes don't need data persistence or authentication—and that's by design. Hard-coded sample data and browser memory are enough for the vast majority of concept tests, design reviews, and moderated research sessions. But occasionally, the question you're trying to answer requires more: a prototype that remembers what users did across sessions, or one where different users can log in and see their own data. When that's the case, you need to know how to add these capabilities without over-engineering your prototype.

In this lesson, you'll learn when persistence and authentication are worth the added complexity, and how to implement them when they are—starting with the simplest approach and building up only as far as your prototype demands.

## 

## The persistence ladder

In [Software Architecture for Non-Technical Builders(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14115:6755/prototyping-fundamentals), we introduced the persistence problem: you build a prototype, enter some data, refresh the page, and everything is gone. We covered where data can live—hard-coded files, browser memory, local storage, cookies, and server-side databases—and why different situations call for different approaches.

Now it's time to put that knowledge into practice. But before we start building, let's revisit a principle from [The New Product Development Lifecycle(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14114:6754/introduction-to-prototyping): prototypes are decision-making tools. Every feature you add should serve the question you're trying to answer. Data persistence and authentication add complexity, and that complexity should be justified—not added reflexively because "real apps have databases."

Think of persistence as a ladder. Each rung adds capability but also complexity. You only climb as high as your prototype needs.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/persistence-ladder.svg)

**Rung 1: Hard-coded data.** Sample data ships with your code. The prototype looks realistic and feels populated, but any changes the user makes exist only in the browser's memory. Refresh, and everything reverts. This is where we started with the retrospective board in [From Prompt to Prototype in Minutes(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14114:6754/introduction-to-prototyping)—and it's perfectly fine for concept prototypes and moderated research sessions where you're watching the user in real time.

**Rung 2: Local storage.** The browser's localStorage saves changes on the user's computer, so data survives refreshes and even closing the browser. This is a single prompt away in most prototyping tools, and it's often all you need for unmoderated testing where users might take a break and come back.

**Rung 3: A server-side database.** Data lives on a server, accessible from any device, shared across all users. When one person adds a card to the retrospective board, everyone sees it. This is the right choice when you're testing collaborative features or running studies where multiple participants interact with shared data.

**Rung 4: Authenticated data persistence.** Users log in, and the system knows who they are. Each person has their own data—their own boards, their own votes, their own identity. This is what you need for diary studies, multi-session testing, or any prototype where users need to pick up where they left off across devices.

Most prototypes need rung 1 or 2. Many need rung 3. Few need rung 4. Let's build all four, starting with the simplest and working our way up.

**Note:** localStorage is tied to the specific URL where your app is running. In most prototyping tools, the embedded preview inside the editor (where you see chat on the left and your app on the right) and the full-screen preview (opened in its own browser tab) run on different URLs. That means they have separate localStorage states—changes you make in one view won't appear in the other. This isn't a problem in practice, since the people you share your prototype with will only ever use a single URL. But it's important to know when debugging: if your saved state seems to have disappeared, check whether you're looking at a different view than the one where you made the changes.

Test it: add a card, upvote a few items, then refresh the page. Your changes are still there. Close the browser entirely, reopen it, navigate back to the prototype—still there. The "Reset Board" button gives you a way to get back to the original state if you need to start fresh.

### Under the hood

If you peek at the code, you'll see something like this:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/Screenshot%202026-03-10%20.jpg)

A few things worth noticing:

- **localStorage is a key-value store.** You give it a name (like 'retro-board-cards') and a value (the JSON-encoded card data). It's essentially a simple dictionary that persists in the browser.
    
- **The data is serialized as JSON.** JSON.stringify converts the cards array into a text string for storage; JSON.parse converts it back when loading. This is the same JSON format we saw with API responses in Lesson 3.2.
    
- **The save happens automatically.** The useEffect hook watches for changes to the cards state. Every time a card is added, upvoted, or deleted, the entire board state is saved to localStorage. You don't need a "Save" button—it just works.
    
- **The reset clears the stored data.** The "Reset Board" button simply calls localStorage.removeItem('retro-board-cards'), which removes the saved data and lets the app fall back to the default sample cards on the next load.
    

## When localStorage is enough

For many prototyping scenarios, this is everything you need. You've built a prototype that feels real—it remembers what users do across sessions, so they can pick up where they left off. Consider these common situations:

- **Moderated research sessions** where you're watching the user in real time. They might refresh accidentally, and localStorage prevents the frustration of losing their work.
    
- **Unmoderated testing** where users interact with the prototype on their own schedule. They can close the browser, come back the next day, and everything is as they left it.
    
- **Internal demos** where you want stakeholders to play with a prototype over a few days and come back to discuss their experience.
    

In all of these cases, you don't need a server-side database. You don't need users to authenticate. You don't need their data to sync across devices. You just need the prototype to remember what happened in _this_ browser. localStorage handles that perfectly.

The limitation is clear: the data lives on one device, in one browser. If the user opens the prototype on their phone after using it on their laptop, they'll see a fresh board. And if two users are on the same prototype, they each see their own separate version—there's no shared state. When you need shared data or cross-device persistence, it's time to climb to rung 3.

## Under the hood

If you look at what Lovable generated, you'll notice it's created database tables that match the data model we specified. The database is managed by Lovable Cloud, which provides a PostgreSQL database—the same type of database used by many production applications. You can see those tables by clicking on the **Cloud** item in the header bar.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/image%20%2824%29.png)

The key difference from our localStorage approach is where the CRUD operations happen:

- **Create:** When a user adds a card, the frontend sends a request to the backend, which inserts a row into the Cards table.
    
- **Read:** When the page loads, the frontend fetches all boards (or a specific board's cards) from the database.
    
- **Update:** When a user upvotes a card, a new row is added to the Votes table, and the card's vote count is recalculated.
    
- **Delete:** When a user deletes a card (after confirmation), the row is removed from the Cards table.
    

These are the same CRUD operations we covered in [Software Architecture for Non-Technical Builders(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14115:6755/prototyping-fundamentals)—now you're seeing them in action.

## Adding authentication

We now have a retrospective board where anyone can create boards, add cards, and vote. That's a useful starting point, but there's no identity. The app doesn't know _who_ is using it. Everyone is anonymous, which means:

- You can't show who added a card.
    
- You can't restrict who can delete a board.
    
- You can't tell whose votes are whose.
    
- If someone closes their browser and comes back, the app has no way to reconnect them to their previous actions.
    

This is where authentication comes in.

### 

## What is authentication?

In [Software Architecture for Non-Technical Builders(opens in a new tab)](https://edu.reforge.com/learn/courses/7165/ai-prototyping/lessons/14115:6755/prototyping-fundamentals), we introduced authentication as one of the three key things the backend handles for every request: routing (where should this go?), authentication (who's asking?), and business logic (what should happen?). Let's go a bit deeper now that we're about to implement it.

**Authentication** is the process of verifying who a user is. When you log in to any app—Gmail, Slack, Netflix—you're authenticating. You provide credentials (usually an email and password), and the server checks them against its records. If they match, you're in. The server creates a **session** that links your browser to your identity, so you don't have to log in again on every page.

**Authorization** is what happens next: determining what you're _allowed_ to do. Authentication tells the system "this is Sarah." Authorization determines "Sarah can edit her own boards but can only view boards created by others." These are related but distinct—you can be authenticated (the system knows who you are) without being authorized (the system might not let you do what you're trying to do).

For most prototypes, authentication is the bigger milestone. Once the system knows who each user is, adding authorization rules is straightforward.

### How login works

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790290800/UoviUdyE0A9VxxSvgzh7GQ/scorm/4c7a9d8af9f1c9ff6100277eff0737e7d11e6a117404ad4be1299da44cd1b846/scormcontent/assets/authentication-login-flow.svg)

The typical login flow has a few steps that happen behind the scenes:

1. **The user enters their email and password** on a login page.
    
2. **The frontend sends those credentials to the backend.** This happens over an encrypted connection (HTTPS) so the password can't be intercepted.
    
3. **The backend checks the credentials** against the database.
    
4. **If the credentials match, the backend creates a session.** The session ID is sent back to the browser as a cookie.
    
5. **Every subsequent request includes the session cookie.** This is how the server knows "this request is from Sarah" without asking her to log in again on every page.
    

This is why clearing your cookies logs you out—the browser no longer sends the session ID, so the server treats you as a stranger.

**How passwords are stored:** Passwords are never stored directly—instead, the system runs each password through a one-way scrambling process (called _hashing_) that turns it into a long, random-looking string of characters. The original password can't be recovered from this string. When you log in, the backend runs the same process on what you typed and checks whether the result matches what's stored. This way, even if someone broke into the database, they'd see scrambled strings—not actual passwords.

Modern authentication services like Lovable Cloud's built-in auth, Auth0, and Clerk handle all of this complexity for you. You don't need to build a login system from scratch—you just need to tell your prototyping tool that you want authentication, and it wires everything up.

## Under the hood

The authentication system adds several pieces to the architecture:

- **A users table** in the database stores account information—email, hashed password, and a unique user ID.
    
- **A session system** manages login state. When a user logs in, the backend creates a session and sends a cookie to the browser. Every subsequent request includes that cookie, so the backend knows who's making the request.
    
- **Foreign keys** connect the data model to users. The Cards table now has a user_id column linking each card to the user who created it. The Boards table has a similar user_id column. The Votes table links each vote to both a card and a user.
    
- **Authorization rules** check permissions before executing actions. Before deleting a board, the backend verifies that the requesting user is the one who created it. Before casting a vote, it checks that this user hasn't already voted on this card.
    

This is the same pattern used by production applications. The difference is scale and polish, not architecture.

## Why add authentication to a prototype?

Adding authentication to a prototype adds a lot of capability but also a lot of complexity. In many cases you won't need it—but there are specific scenarios where it's exactly what you need:

**Diary studies.** When the same users interact with your prototype over days or weeks, authentication lets each participant pick up where they left off. Their boards, cards, and votes persist across sessions and devices.

**Multi-user collaboration testing.** If you're testing a feature that involves multiple people working together—like our retrospective board—authentication lets you observe how users interact with each other's contributions. Who builds on someone else's idea? Who reorganizes action items? These collaborative dynamics only emerge when identity is part of the experience.

**Role-based experiences.** If you need to test how different types of users experience the same product—an admin vs. a team member, a manager vs. an individual contributor—authentication gives you a way to assign roles and show different UI based on who's logged in.

**Quantitative analysis.** When each action is tied to a specific user, you can analyze behavior patterns across participants—who engaged most, which features were used by which cohorts, how behavior changed over time.

If none of these apply to your prototype, you probably don't need authentication. Stay on a lower rung of the persistence ladder.

## Bringing it all together

We now have a fully working retrospective board—one that could, with a bit of iteration, be deployed for your team's actual retrospectives. Lovable makes this straightforward: your app is already running in the cloud, and sharing it is as simple as sharing a URL.

We built the app quickly, and that speed illustrates the power of AI tools to create functional software in hours rather than weeks. That's both a blessing and a challenge. It enables us to create working software faster than ever before—but if we don't know what questions we're trying to answer with our prototypes, we'll find ourselves with a lot of polished software and very few insights.

Here's the progression we followed in this lesson:

1. **Hard-coded data** — a prototype that feels real until you refresh.
    
2. **Local storage** — changes survive refreshes and browser restarts, with a single prompt.
    
3. **A server-side database** — shared state across users and devices.
    
4. **Authentication** — individual identity, personalized experiences, and authorization rules.
    

At each step, we added complexity because the question we were trying to answer required it. That's the principle to carry forward: climb the persistence ladder only as high as your prototype demands.

Just as important as _what_ we built is _why_ we built it. The next lessons will look at how to integrate prototypes into your process: aligning teams around a shared vision, improving your customer discovery through realistic testing, and handing off to engineering so they can build the best possible version of the features you've validated.
