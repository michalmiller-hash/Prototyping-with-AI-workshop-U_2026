Context engineering means giving your AI prototyping tool the same clarity a well-run product team gives its engineers. In this lesson, you'll learn how AI models use context to generate code, then apply that understanding through three practical approaches—functional, visual, and data—that produce results that look, feel, and behave like your actual product. After learning each approach individually, you'll combine all three into a single structured prompt that dramatically improves output quality.

In the last module, you built a functional prototype from a short text prompt. At first glance, the result was impressive. On closer inspection, there were important gaps: the prototype looked generic, used fake data, didn't handle edge cases well, and had no data persistence.

This lesson is about closing those gaps. You'll learn about context engineering—how to provide AI prototyping tools with the right information to produce results that look, feel, and behave like your actual product. We'll cover three practical approaches to providing context—functional, visual, and data—and techniques for managing context as your prototypes grow more complex.

## What is context engineering?

### From prompt engineering to context engineering

For a couple of years, the conversation around AI focused on "prompt engineering"—the art of phrasing your request just right. But as AI tools have gotten more capable, “prompting” doesn’t fully describe the task at hand. Shopify CEO Tobi Lütke captured this shift well:

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/Screenshot%202026-03-02%20.png)

That gives us a clear definition for context engineering:

**Context engineering** is designing and building systems that provide an AI model with the right information & tools to accomplish a task.

## How LLMs use context

To understand why context matters so much, it helps to remind ourselves how these models actually work.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/AI%20Product%20Management..jpg)

An LLM (large language model) takes an **input** (your prompt) and combines it with **context** (such as system instructions, prior messages, a reasoning plan/todo list, etc.) before the **model** generates a response. When needed, it can also use **tools**—external systems like search, calculators, databases, or code execution—to fetch facts, run calculations, or perform actions to add context. The model then brings everything together—your prompt, the surrounding context, and any information retrieved by tools—to generate the final **output**. This is why context matters so much: the model's training gives it general capability, but the context you provide is what makes the output specific and useful.

Prototyping tools push this to the limit. Instead of generating a paragraph of English, they generate thousands of lines of code spread over dozens of files—all working together to produce a functional application. For this reason, context is critically important. The more complete and specific the context, the better the output.

## Context engineering from first principles

Context engineering matters now because the biggest gains in AI quality aren't just coming from better models—they're coming from better context. Here's how that happened.

In 2024, a lot of innovation came from improvements in **training**—making the models themselves smarter. In 2025, the improvements shifted to **inference**—how models process and reason about what you give them. To generate more sophisticated answers, LLMs evolved to work with more sophisticated contexts.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/cUCQcB/AI%20Product%20Management..jpg)

Here's a rough timeline of that evolution. Early systems began with **single-step completions** (e.g., GPT-3): you provide an input snippet, and the model generates the most likely continuation. No conversation, no memory—just a single pass.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/RYg-JO/AI%20Product%20Management..jpg)

Then came **chatbots** (early ChatGPT), which could sustain conversation by feeding the model a running transcript of prior exchanges. Each new message is appended to a **context window** that includes all previous turns, and the model produces its reply as a completion of that full conversation so far.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/GCaIsH/AI%20Product%20Management..jpg)

Next came **retrieval augmented generation** (RAG). RAG solves a critical problem: training data is frozen in time. Remember the "My training cut-off date is September 2021" message in early versions of ChatGPT? RAG addresses this by enabling tools like Perplexity, ChatGPT, and Claude to search the web before answering, grounding responses in the latest information rather than just training data.

From there, models gained **tool use**, enabling them to call external systems. In fact, the web search in RAG is itself an early form of tool use. This was a step change: instead of just generating text based on what they already knew or could retrieve, models could now _take actions_—searching databases, running code, calling APIs, and even navigating software interfaces. Tool use shows up in a few different forms:

- **MCP (Model Context Protocol)** is an open standard that lets AI models connect to external data sources and services through a universal interface—think of it as a USB-C port for AI tools.
    
- **Connectors** are pre-built integrations (like Notion AI's Slack or Google Drive connectors) that give models access to specific apps and data without custom setup.
    
- **Computer use** lets models interact directly with software interfaces—clicking buttons, filling out forms, navigating menus—the way a human would.
    

The common thread: each of these expands the model's context beyond what's in the prompt or the training data, letting it pull in live information and perform real work.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/_E9kUF/AI%20Product%20Management..jpg)

Most recently—and most relevant for prototyping—**reasoning models** made it possible to build full, working applications from simple prompts. Reasoning models work by **breaking your request into a checklist of subtasks**, then working through them—using tools to gather information, run checks, and verify results. As they complete steps, they can update the plan based on what they learn (for example, adjusting if a source contradicts an assumption), and keep iterating until the plan is complete.

![](https://cdn5.dcbstatic.com/files/r/e/reforge_docebosaas_com/1790107200/QtKQYJgQdVGbdX-CKbHBYg/scorm/7568fc9c96181f8cbcc1e230be3b9b396dd7eec853a773a3edbe1d54ec9492b9/scormcontent/assets/image.png)

Many vibe coding tools allow you to turn Plan Mode on and off, enabling you to choose between a quick response and a more elaborate one that uses advanced reasoning capabilities. With Plan Mode on, you can use a relatively simple prompt, like the one from the lesson "From Prompt to Prototyping in Minutes," to build a sophisticated prototype. The reasoning model turns terse instructions into a robust plan to build fully functioning software. It fills in the gaps.

But every gap the model fills is a decision made without you. The more context you provide—about how the software should behave, what it should look like, and what data it should use—the fewer gaps the model fills on its own. Let’s look at how to do that in practice.

## What your prototyping tool needs to know

A lot goes into defining what needs to get built. Strategy docs, OKRs, design systems, PRDs, wireframes, detailed designs, technical design documents—you're constantly creating artifacts that give your team the information they need. Your prototyping tool needs similarly well-thought-out context.

The context you provide generally falls into three pillars:

- **Functional context** defines what the software _does_—its features, user interactions, and behavior across different states.
    
- **Visual context** defines what the software _looks like_—its layout, design language, and user experience.
    
- **Data context** defines how the software _works_—the structure, relationships, and realistic sample content that power the experience.
    

Most people start with functional context, but as we'll see, the other two pillars—visual context and data context—are just as important to getting the desired output from your prototyping tool.

How much context you provide depends on where you are in the product lifecycle. In the lesson "The New Product Development Lifecycle," we looked at four types of prototypes: concept prototypes, design prototypes, research prototypes, and technical prototypes. You'll need different amounts of context depending on which type you're building, what question you're answering, and where you are in your product lifecycle.

## Functional context—Use cases & behavior

Functional context is the most natural starting point for product managers—it maps directly to how we already think about product requirements. A functional prompt describes the behavior you want the software to perform, similar to the details you'd write in a spec, PRD, or user story.

Our prompt from the lesson "From Prompt to Prototyping in Minutes" is a functional prompt:

_Build a team retrospective board with three columns:_  
_* "What went well" (green)_    
_* "What didn't go well" (red)_  
_* "Action items" (blue)_  

_Users should be able to:_  
_1. Add new cards to any column_  
_2. Upvote cards they agree with_  
_3. See cards sorted by vote count within each column_    
  
_Use a clean, minimal design. Include 2-3 sample cards in each column to start._

Notice that this prompt is specific about behaviors, not just features—it doesn't just say "add voting," it specifies that users upvote and cards sort by vote count.

Good functional contexts follow a few best practices:

- **Be specific (unless you're brainstorming).** Go beyond naming a feature ("add a filter") and describe the behavior precisely: what triggers it, what it affects, what the states look like. The exception is brainstorming—a vague prompt lets the AI interpret your request in unexpected ways, giving you a wider range of ideas to react to.
    
- **Describe edge cases, not just the happy path.** Most functional prompts describe what happens when everything works, but not what happens when it doesn't. Think through affordances (i.e., interactions, such as hover states, to help users when they are confused), empty states (how to help the user get started), loading states (what happens when the user is waiting), and error states (what’s the experience when things go wrong).
    
- **Default to “do” over “don’t.”** LLMs are better at hitting a target than avoiding one. “Use a clean, minimal design with generous whitespace between columns” gives the model something concrete to aim for. Negative requirements, like “Don’t make it cluttered”, leave too much room for interpretation.
    
- **Break down complex requirements.** Reasoning models break complex requirements into smaller tasks on their own, but it's sometimes good to give the LLM a helping hand. Use Markdown formatting—headers, numbered lists, sub-bullets—to organize a detailed prompt, or split complex requirements across multiple prompts. For example, use the first prompt to establish overall navigation, the second to describe how the user views data, and the third to add details for creating and editing items.

## Visual context—Design & UX

Would you ever build a house without blueprints? Of course not—the architect could give you the most detailed written spec in the world, but the plan is not complete until you can see it. The same is true for software. Visual context—wireframes, references, and detailed designs—serve as the blueprint that removes ambiguity and gives your team a shared picture of what you're building.

Prototyping tools benefit just as much. Without visual reference, AI tools fall back on generic defaults—they're trained on thousands of public code repositories, so when you ask for a form, you get what most forms look like across the internet. You get a least-common-denominator design.

Visual context helps you break away from those defaults. It falls into three categories:

1. **Design references** provide the look and feel of your product—your color palette, typography, component styles. Attaching a screenshot of your existing product or design system gives the AI a visual vocabulary to work from. This is the single fastest way to make a prototype look less generic.
    
2. **Wireframes** establish layout and interaction patterns. Your wireframes can be rough—photos of hand-drawn sketches or quick layouts in Balsamiq work surprisingly well. The AI is remarkably good at interpreting rough wireframes and turning them into polished interfaces, especially when combined with a design reference.
    
3. **Detailed designs**, created by dedicated designers, provide a high-fidelity definition for your product’s UX and visuals. These aren’t always necessary. They tend to be valuable in the later stages of the product lifecycle, particularly when putting prototypes in front of real users. Your prototyping tool will attempt to match the detailed designs, but pixel-perfect reproduction may take more time than it's worth. Remember: the goal of a prototype is to help you make better decisions heading into production, not to be production-ready itself.
    

**Importantly, you don't need to be a designer to provide visual context—a rough sketch or a screenshot of an existing product is enough to dramatically improve your results.** Some prototyping tools have features to make this even easier. For example, the [Reforge Build Extension(opens in a new tab)](https://www.notion.so/2-1-Context-Engineering-for-Prototyping-aa9e9c97540c4c16bfac168eabc8e2f2?pvs=21) is a Chrome plug-in that allows you to capture pages, flows, components, and design systems from your existing product. We'll take a closer look at the Reforge Build Extension in our next lesson.

Visual context works even better when paired with written descriptions. You can tell the AI exactly what you're providing and how to use it:

_The attached screenshot shows our current product. Match the color scheme and typography, but use the wireframe layout for the new feature._

## Data context—Schema & mock data

Between functional and visual context, you can produce prototypes that look and behave like real software. But there's a missing piece that often gets overlooked.

The data powering your prototype matters as much as the design and functionality—yet most people leave it entirely to the AI's imagination. And it shows. Generic names, broken images, poor copy, and unrealistic metadata. Imagine the "Eiffel Tower" appearing with a "Hidden Gem" badge. These kinds of errors break "suspension of disbelief." Users stop engaging naturally, and your research is compromised before it begins.

Data context consists of two elements:

1. **Schema** (the structure and relationships of your data)
    
2. **Mock data** (realistic sample content that populates the prototype)
    

For most PMs, defining data context requires developing a new muscle. We're used to writing specs and working with designers, but we typically leave data modeling to engineering. When prototyping, thinking deeply about the data is what separates a toy from a tool.

We saw this firsthand with our functional prototype of the Genre Discovery Page. The AI-generated data is passable but not authentic enough to pass for a real product feature.

By providing a realistic data set with a well-defined schema, we get two benefits: a more convincing prototype, and better separation of concerns. As we'll see below, this means we can swap the Downtempo data set for a different genre without touching the code.

A few best practices before we put this into action:

- **Define your schema first.** Think about entities, fields, and relationships before you open your prototyping tool. For our music example, that means deciding that "albums" and "artists" are your main objects, each album has a name, release date, cover image, and tags, and each album is linked to an artist.
    
- **Prioritize real data.** Use realistic names, plausible quantities, and real images wherever possible. If you have access to production data, export a scrubbed sample—it almost always feels more convincing than purely synthetic data.
    
- **Use a dedicated tool for data generation.** Generating data in a separate tool (like Claude) and feeding it into your prototyping tool often produces better results. Think of this like rolling your own multi-agent system. You can spin up threads to generate and iterate on data while preserving your prototyping tool's context window for building.
    

### Data context in action

Your prototyping tool is often not the best place to create a good data set. You may already have representative data from your product that you can export and use directly. But when you don't—or when you need to supplement what you have—generative AI tools like Claude and ChatGPT can create remarkably realistic data sets. I like to generate and refine data separately, then feed the finished result into my prototyping tool. This keeps the prototyping tool's context window focused on building, and it means I can tap into MCP servers to pull real images from [Unsplash(opens in a new tab)](https://github.com/hellokaton/unsplash-mcp-server) or data from my own databases.

## Pulling it all together

Each type of context contributes something distinct. Functional context defines behavior. Visual context sets the look and feel. Data context provides realism. Now let's combine all three into a single prompt for our Genre Discovery Page:

# Build a Music Genre Discovery Feature

## Functionality
Build a music genre evolution page for "Downtempo" with the following sections:

* Hero image - a large placeholder image at the top
* Genre header - display the genre name as a bold title, followed by a multi-sentence description paragraph
* Artist tags- a wrapping row of clickable pill tags listing key artists associated with the genre
* Album timeline - a chronological list of landmark albums, grouped by year. Each entry should include: 
    - The year as a section header with a horizontal divider line
    - Album artwork thumbnail
    - Artist name and album title
    - A short description of the album's significance
    - A set of genre/style tags (e.g. "trip-hop", "dub", "bristol sound")

## Design 
* Design the page based on the attached wireframe.
* Use a dark theme with full rounded buttons. Use this green as the primary color: #1ed760. Use dark gray for the cards #1f1f1f and even darker gray for the background.


## Data
* Populate the page with real Downtempo content using the following data. 
* Make sure to use all of the data provided. 
* Use cover_url as the album cover image for each album in milestone_albums
* Save this data to a separate file called data.json.
 
[ Paste in the JSON data and attach the wireframe ]

Of course, there are things to refine before putting this in front of customers. The header placeholder image, for example, takes up a lot of space. That surfaces a classic product management question:

- Remove it to bring content higher up the page?
    
- Hardcode a single header image shared across all genres?
    
- Add the header image to the data set so each genre gets its own?
    

A prototype should help you make exactly these kinds of decisions—and the richer the context, the faster you get there.

That's the core difference between vibe coding and context engineering. Vibe coding asks the AI to figure everything out from a loose description. Context engineering gives the AI the same clarity a well-run product team gives its engineers—clear requirements across design, behavior, and data—so it can focus on building rather than guessing.
